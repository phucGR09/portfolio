N+1 Query

Data & Database Foundational Expensive

Your candidate list loads instantly with 10 rows. With 500, it crawls.

101 queries → 2 queries

Classic problem

The situation

An applicant tracking page lists candidates with their company name next to each one. The first version was simple: load the candidates, then for each one ask the database for its company. That is exactly how you would describe the task out loud — "for each candidate, look up their company" — so it is exactly how the code reads, and it passed review. It was also tested against five rows of fixture data, where one extra query per row is free. Nobody wrote a bug; they wrote a sentence, and the database bill for a sentence depends entirely on how many times you say it.

Under the hood

Naive mode runs one query to list candidates, then one more query per candidate to fetch its company — N+1 round-trips for N rows. Principled mode runs the same candidate query, then a single batched query for every company referenced, and joins the two in memory with a lookup map. The data returned is identical; only the number of round-trips changes.

The principle

Fetching related data inside a loop multiplies your query count by the size of the loop. Batch the lookups instead: fetch once, then join in memory.

Trade-offs & when NOT to

Apply this when

You are joining a small-to-medium set of foreign keys against a table that is cheap to fetch in bulk — companies, categories, any lookup table the loop keeps hitting one row at a time.

Don't when

The batched result would be too large to hold in memory, or each row genuinely needs a different external call (a different API per row, not a different database row). Then the fix is pagination or streaming, not one big batch.

Where this bites in practice

Lazy-loading ORMs are the usual source: ActiveRecord, Eloquent, Hibernate, and Django's ORM all let a simple property access (candidate.company.name) trigger a hidden query. The loop looks completely innocent in the diff. The early sign is a page that "feels slow" only once it meets real data — fixture tests with five rows never show the cost, because five extra queries are free and five hundred are not.

Carry it away

  • When a page feels slow, count the queries first — not just the response time.
  • Reach for eager-loading (.select_related(), .includes(), a manual batch query) before reaching for caching.
  • A database call inside a loop is worth a second look, every time, regardless of how natural the sentence reads.
  • Batching changes round-trip count, not correctness — the two modes above return identical data.
