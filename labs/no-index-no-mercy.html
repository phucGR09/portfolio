Missing Index

Performance & Scale Intermediate Expensive

Searching candidates by email was instant at 1,000 rows. At 50,000, it takes half a second.

50,000 rows scanned → 1 row scanned

Classic problem

The situation

An admin screen lets a recruiter look up a candidate by email. It was built against a few hundred test rows, so a plain WHERE email = ? query felt instant — there was nothing to optimize yet, and adding an index to a table that small wouldn't have changed anything a human could perceive. Months later the candidates table has grown to 50,000 rows the same way real tables do: one signup at a time, with no single commit that made it "big." The query never changed. The table just kept growing underneath it, and nobody was watching the one number that mattered: how many rows the database has to look at to answer this question.

Under the hood

With no index, a row has no fixed address the database can jump to — the only way to find it is to check rows one at a time until a match turns up, which means checking all of them in the worst case. A B-tree index keeps a sorted, searchable copy of the column being searched, so each comparison can discard roughly half of what's left, the same way a phone book lets you skip to "M" instead of reading every name. 50,000 rows at one comparison each becomes about 16 comparisons at two per step (log2 50,000 ≈ 16). That speedup isn't free: the index itself has to be updated on every insert, so writes get slower and the table takes more disk space — which is why an index is a trade a team makes on purpose for a column it searches often, not something to add to every column by default.

The principle

A database table has no memory of where a row lives unless something tells it. Without an index, finding a row means looking at all of them; with one, finding a row means following a structure built for exactly that question — but every structure has to be kept up to date, and that cost lands on every write, not just the reads it speeds up.

Trade-offs & when NOT to

Apply this when

A column is searched or filtered on often, the table is large enough that a scan is measurable, and writes to that column are comparatively rare — the classic case is a lookup key like email, username, or an external ID.

Don't when

The table is small enough that a full scan is already sub-millisecond, the column is written far more often than it's searched, or you're tempted to index every column "just in case" — each extra index is more write cost and storage for a read pattern that may never happen.

Where this bites in practice

Admin and reporting screens are the usual victims — they're built early against a mostly empty table, work fine for months, and nobody revisits the query once it's shipped. The early sign: a query that filters or sorts on a column with no index, on a table whose row count you can't name offhand. If "how big is this table now?" isn't a number someone already knows, the query is at risk of degrading silently until a user notices first.

Carry it away

  • Any column in a frequent WHERE, JOIN, or ORDER BY clause on a table that will grow is a candidate for an index.
  • An index speeds up reads on that column and slows down every write to it — add indexes on purpose, not by default.
  • "It's fast in dev" means nothing if dev has 200 rows and production will have 200,000.
  • Know the row count of your largest tables. A query's cost is a function of that number, whether anyone is tracking it or not.
