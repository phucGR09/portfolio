SQL Injection

Security & Trust Foundational Catastrophic

A contact form started returning every customer's password hash.

One quote character → the entire users table

Classic problem

The situation

A "contact us" form checks whether the submitted email already has an account, so it can show a slightly different message. The engineer wrote the lookup by hand and glued the submitted email directly into the query text — the fastest way to ship the feature, and an email field felt like the last place anyone would think to attack. A contact form isn't an admin panel; it didn't occur to anyone that it was also a database interface.

Under the hood

The query text is one fixed string plus the submitted value plus a closing quote. A normal email has no quote character in it, so the value stays inside the literal. ' OR '1'='1 contains one: it closes the literal early, and everything after it — OR '1'='1 — is read as part of the SQL grammar, not as data. '1'='1' is always true, so the condition matches every row. A parameterized query never pastes the value into the query text in the first place, so this trick has nothing to attach to.

The principle

User input is data, never code. Gluing strings together lets input change the grammar of the query; a parameterized query keeps input as a value no matter what characters it contains.

Trade-offs & when NOT to

Apply this when

Any query, filter, or command built from user-controlled text — form fields, URL parameters, headers, even values forwarded from another internal service you don't fully trust.

Don't when

You're composing the query's structure itself — a table name, a column to sort by — which a parameter can't represent. Those need a vetted allow-list, not string interpolation and not a bind parameter either.

Where this bites in practice

Hand-rolled query builders, legacy code from before the team adopted an ORM, and "quick admin scripts" that skip the ORM for one query are the usual sources. The early sign a reviewer can catch in seconds: string concatenation or template-literal interpolation sitting directly inside a SQL string.

Carry it away

  • Treat every external string as data, never as code.
  • Use your ORM or query builder's parameter binding for every value, with no exceptions for "just this one query".
  • Table and column names can't be parameters — validate those against an allow-list.
  • If a diff shows string concatenation building a query, stop and ask why before merging.
