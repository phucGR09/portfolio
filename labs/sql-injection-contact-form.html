SQL Injection

Security & Trust Foundational Catastrophic

A login page let someone in without the right password.

One crafted email → a workspace that wasn't theirs

Classic problem

The situation

Northstar is a fictional project workspace with an ordinary email-and-password login. Its legacy backend builds a SQL query by joining the submitted email to a password condition, then creates a session if a row matches. A crafted email closes the quoted value and comments out the password condition. The wrong password is still submitted, but the database no longer checks it. Try the login below to see the consequence: the workspace opens for someone who does not know the account's password.

Under the hood

In the vulnerable implementation, the email becomes part of the query text. The targeted attack ends that quoted value with ', then starts a SQL comment with -- , removing the password predicate. The second attack also adds OR '1'='1', an always-true condition; the login uses the first matching account. In the parameterized implementation, the query keeps its ? placeholders and receives both values separately, so neither input can change its grammar. Browser email validation is useful feedback, but a client can send a request directly to the API. The attack cards explicitly replay that path.

This simulation uses fake password markers to isolate the SQL behavior of a legacy login. For a real login, bind the email lookup, then verify a securely stored password hash with a suitable password library. Do not store plaintext passwords or copy the demo's marker comparison into production.

The principle

User input is data, never code. Gluing strings together lets input change the grammar of the query; a parameterized query keeps input as a value no matter what characters it contains.

Trade-offs & when NOT to

Apply this when

Any query, filter, or command built from user-controlled text — form fields, URL parameters, headers, even values forwarded from another internal service you don't fully trust.

Don't when

You're composing the query's structure itself — a table name, a column to sort by — which a parameter can't represent. Those need a vetted allow-list, not string interpolation and not a bind parameter either.

Where this bites in practice

Login endpoints, password-reset lookups, account searches, and admin filters can all receive attacker-controlled input. A vulnerable login is especially direct: if the handler creates a session from a query whose password condition can be removed, injection becomes an account takeover. Review the server query and session creation, not just the email field's browser validation. Look for string concatenation or template-literal interpolation inside SQL, including raw queries issued through an ORM.

Carry it away

  • Treat every external string as data, never as code.
  • Use your ORM or query builder's parameter binding for every value, with no exceptions for "just this one query".
  • Table and column names can't be parameters — validate those against an allow-list.
  • If a diff shows string concatenation building a query, stop and ask why before merging.
